# Game skill business plan

## Product

Working name: **Config-Driven Arcade Game Builder**

Core promise: help a developer or small studio audit, extend, and ship a TypeScript/React/Pixi arcade game with a real gameplay/editor architecture, safe asset configuration, lifecycle discipline, focused tests, and honest production boundaries.

The first deliverable is the installed `build-pixi-arcade-games` Codex skill. Scicon Shooter is the proof project, but Scicon branding, proprietary secrets, live credentials, and project-specific art are not part of the generic product.

[OpenAI's current skills documentation](https://developers.openai.com/codex/skills) says skills package reusable instructions, resources, and scripts, while plugins are the distribution format for other people to install. The local distribution package is `config-driven-arcade-game-builder`, version `0.1.0`.

## Demonstrable proof

- One canonical Pixi game surface shared by production and a local level editor.
- Configuration-driven waves, bosses, assets, HUD, and record presentation.
- Strict catalogs and validation for built-in and generated art.
- Fixed-step simulation with manual Pixi rendering and adaptive mobile caps.
- Loopback-only, versioned, reversible authoring workflow excluded from production.
- Verified-run, leaderboard, wallet, and collectible boundaries with explicit truth rules.
- A current green baseline of 196 automated tests across the game and Director, plus typechecks and a production build.

Do not advertise “cheat-proof,” guaranteed performance, guaranteed sales, official ResearchHub status, or autonomous production publishing.

## Offer ladder to validate

These are offer hypotheses, not validated market prices:

1. Free architecture checklist and repository audit sample.
2. Paid skill pack with the workflow, audit script, reference architecture, and update access.
3. Repository-specific architecture audit with a prioritized implementation plan.
4. Fixed-scope prototype or feature implementation using the skill.
5. Ongoing tuning, performance, test, and authoring-tool support.

Price only after reviewing comparable current offerings, expected support load, licensing, and the sales channel. Keep implementation services separate from a self-serve skill license so buyers understand what is and is not included.

## Ideal early customers

- Indie web-game developers moving from canvas prototypes to maintainable Pixi architecture.
- Small studios that need a configuration-driven level or wave editor.
- Community or onchain apps that need guest-first gameplay and truthful wallet/record boundaries.
- Agencies building branded arcade activations that require a repeatable test and delivery process.

## Draft listing copy

**Build browser arcade games that stay editable, testable, and shippable.**

Config-Driven Arcade Game Builder gives Codex a practical workflow for TypeScript, React, and PixiJS games. It helps route changes to the right layer, preserve one canonical game/editor surface, validate campaign and asset data, protect lifecycle and mobile performance, and verify the complete production boundary before handoff.

Includes a read-only repository audit script, a reference architecture derived from a working game, implementation and verification checklists, and guidance for optional score, wallet, and local-authoring systems.

## Launch assets to prepare

- A sanitized architecture diagram with no secrets or customer-owned artwork.
- A short before/after example showing a duplicated preview replaced by one shared game stage.
- A screen recording of a safe campaign edit flowing into the real game preview.
- A sample audit report generated from an open or purpose-built demo repository.
- Clear license, support window, refund terms, privacy statement, and version policy.

## Staged launch

1. Validate the plugin locally and run it on a sanitized demo repository.
2. Decide ownership, license, included support, refund policy, and initial beta price.
3. Publish a free architecture checklist and a short proof video to earn trust.
4. Invite a small beta group and measure installs, successful audits, support time, and requested features.
5. Revise the skill from observed failures before broad promotion.
6. Open one paid channel, then add another only when attribution shows why it is needed.

## Approval boundary

Nothing in this plan authorizes creating seller accounts, publishing a listing, posting on social media, messaging communities, using customer data, spending money, or promising support terms. Choose the channel, legal owner, license, price, and public claims first; then explicitly approve the external action.
